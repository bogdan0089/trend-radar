# Архітектура

## Потік

```
HTTP  →  router  →  service  →  repository  →  PostgreSQL
                       ↓
Celery →  task    →  service  →  repository
                       ↓
                    scraper / llm / scoring (зовнішній світ і чиста математика)
```

Той самий сервісний шар обслуговує і HTTP, і Celery. Таска — це такий самий тонкий
виклик, як і роутер.

## Шари й правила

### `app/api/routers/` — транспорт
- Валідує вхід (Pydantic-схема), викликає **один** метод сервісу, повертає схему.
- **Не** містить бізнес-логіки, циклів по даних, запитів до БД.
- Тільки тут живуть `HTTPException` і HTTP-статуси.

### `app/services/` — бізнес-логіка
- Уся логіка: правила, підрахунки, оркестрація, звіти про імпорт.
- Володіє транзакцією: сервіс вирішує, коли `commit`.
- Кидає доменні винятки з `app/core/exceptions.py`, **не** `HTTPException` —
  сервіс не знає, що він під HTTP.
- Не знає про `Request`, `Depends`, Celery.

### `app/repositories/` — доступ до даних
- Тільки SQLAlchemy-запити: `get`, `list`, `create`, `update`, `upsert`.
- **Ніколи** не комітить (максимум `flush()`, щоб отримати id).
- Жодних правил і рішень. Якщо в репозиторії зʼявилось `if` про бізнес — воно не туди.

### `app/models/` — ORM-моделі. Тільки схема, без методів з логікою.
### `app/schemas/` — Pydantic DTO для входу/виходу API. ORM-моделі назовні не віддаємо.
### `app/tasks/` — Celery-таски. Тонкі: відкрити сесію, викликати сервіс, залогувати.
### `app/core/` — конфіг, логування, безпека (JWT/хеші), доменні винятки.
### `app/integrations/` — зовнішній світ: Playwright-скрапери, LLM-адаптери.
  Ізольовані за інтерфейсом, щоб сервіс не залежав від конкретного провайдера.

## Транзакції

- HTTP: `get_db` віддає сесію, сервіс комітить, роутер не втручається.
- Celery: `session_scope()` — комітить на виході, відкочує на винятку.
- Репозиторій отримує сесію ззовні і ніколи нею не керує.

## Логування

Один конфіг у `app/core/logging.py`, підключається в `main.py` і в `celery_app.py`.
Логер береться як `logging.getLogger(__name__)` — по імені модуля видно шар.

Що логуємо обовʼязково:
- старт/фініш кожної Celery-таски з тривалістю і результатом;
- кожну спробу скрапінгу: URL, скільки знайдено, чи спрацював антибот;
- вибір скорингу: `llm` чи `fallback` і **чому** (нема ключа / таймаут / невалідний JSON);
- усі відмови авторизації.

Чого не логуємо: паролі, токени, `LLM_API_KEY`.
